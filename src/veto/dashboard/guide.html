How Veto works

Veto checks an agent's proposed payment against a mandate before any executor can act. This guide explains the controls visible in the demo and the limits of the local simulation.

1Write a mandateDefine spending and evidence rules.
2Evaluate a proposalCheck policy against confirmed history.
3Execute or blockOnly approved actions reach an executor.
4Record evidencePreserve decisions and receipts in the audit chain.

Quick start

Start the local server from the repository root, then open the dashboard. No payment keys or money are needed.

python -m pip install -e '.[server]'
python -m veto.api
  1. Open the dashboard and choose Run guided flow.
  2. Inspect the invoice match, wrong invoice rejection, matching payout approval, and duplicate rejection.
  3. Use the metric links, latest result, and audit filters to inspect the recorded reasons and receipt.
  4. Choose USD in the currency selector to see the active mandate reject an uncovered currency.

For a clean repeat, start the server with a fresh database path: python -m veto.api --db ./fresh-demo.sqlite3.

Mandates

A mandate is a text policy that describes what an agent may propose. This demo's VetoDemo mandate allows vendor_123 to receive INR payouts up to ₹100 over a rolling 24-hour window, after matching invoice evidence is recorded.

mandate VetoDemo {
  rule InvoiceGuard {
    cap payout <= 100 INR per 24h
    allow_merchant "vendor_123"
    require invoice_match before payout
  }
}

The grammar also supports USD caps, denied merchants, validity windows, and action sequences. The dashboard shows the loaded mandate under Mandate.

Static checks

Before a mandate is used, the parser produces typed rules. Fast checks report duplicate rule IDs, conflicting merchant lists, inverted time windows, repeated or shadowed caps, and invalid preconditions. Optional Z3 checks whether action-order rules contain cycles that prevent completion.

These checks inspect the policy itself. They do not decide whether a particular proposed payout should run; the runtime guard makes that decision using current time and confirmed history.

Runtime guard

VetoGate checks the action type, amount, currency, merchant, validity window, spending cap, invoice ID, and prior confirmed actions. A money-moving action without a matching cap is rejected. The agent cannot supply the trusted clock or invent confirmed history.

The result includes an approval or rejection reason and, when applicable, a violation code. A rejection is never sent to an executor. Try changing the vendor, amount, invoice, or currency in the proposal form.

Invoice evidence

Click Record invoice match to check the invoice ID against the server-owned demo catalog. The match records its trusted merchant, currency, and total. A payout must refer to a confirmed match, use the same vendor and currency, and equal the catalog total. One confirmed invoice ID cannot authorize a second confirmed payout.

Demo boundaryThe catalog is fixed demo data, not a live accounting or document-verification integration. Production use needs an authenticated source system and document controls.

Execution and replay

The pipeline evaluates a proposal, saves an approved pending intent, then calls an executor with a stable idempotency key. The local dashboard uses a simulated executor. Only a confirmed receipt enters confirmed history, and that history update commits with its approved audit entry.

Repeating the same event ID and action returns the recorded result without executing again. Reusing an event ID for a different action fails. A definite execution failure does not create confirmed history.

Audit trail

Every final decision is stored with the action, reason, time, policy fingerprint, and receipt when available. Each entry hashes its content with the previous entry's hash. The dashboard verifies the chain and lets you filter by decision or search event, vendor, and invoice IDs.

The chain reveals ordinary local edits or deletions. It is not externally anchored or signed, so someone able to rewrite and rehash the entire database could forge a new chain.

Pending recovery

An uncertain external outcome is left pending, not counted as a confirmed payment. The intent survives a restart and blocks unrelated new actions until the same event is retried safely or reconciled against the provider. The Pending panel exposes unresolved local intents.

The browser dashboard uses simulation. The Modern Treasury sandbox command supports explicit GET-only reconciliation; a signed payment_order.completed webhook can trigger that same provider verification when configured with the sandbox webhook key and the same database. Other status events remain pending. SQLite locking protects processes sharing one file; multi-instance deployments need shared durable storage and coordination.

Currencies

Actions can use INR or USD, but approval requires a mandate cap in that currency. This workspace has only an INR payout cap. The currency selector lets you submit USD to see the policy reject it; it does not convert money or switch the active mandate. The separate Modern Treasury sandbox demo uses a USD mandate and a different database.

Provider demos

Modern Treasury

A separate command previews a guarded USD sandbox payout. With --execute, it uses a sandbox organization and accounts, checks the key's mode, and creates an ACH payment order only after policy approval. Orders that are not completed remain unconfirmed.

python -m veto.modern_treasury_demo

Razorpay

A separate command previews a guarded INR test refund against a captured test payment. Test credentials are read only with --execute. RazorpayX payout support is also implemented and covered by mocked HTTP tests.

python -m veto.razorpay_refund_demo

These provider commands are separate from the browser dashboard. The dashboard never loads their keys or sends provider requests.

Local API

The dashboard and API share one SQLite database. The HTTP server binds to loopback by default. Use the interactive API reference to inspect requests and responses.

GET /api/statusCounts and audit integrity
GET /api/policyActive mandate text
GET /api/demo/invoices/nextNext trusted demo invoice fixture
POST /api/demo/invoice-matchesValidate and record invoice evidence
POST /api/proposalsEvaluated payout proposal
POST /api/demo/resetClear simulated data after confirmation
